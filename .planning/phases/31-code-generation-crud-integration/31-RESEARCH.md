## 2. Input Type Handling

### generateFormFieldCode() (modelgen.go:2295)
Generates inline Go code for form fields based on `field.Input`:
- **textarea**: `core.Textarea()` with full-width layout
- **select** (or FK relation): `core.Select()` with dynamic options from relation or static options
- **bool**: `core.Input(type="checkbox")` with checked state
- **default**: Calls `{model}FormField()` helper — infers type from field name (email → "email", password → "password") or field type (int/uint/float64 → "number")

**Pattern for adding "file" input type**: Add a new `case field.Input == "file"` in the switch statement that generates `ui.FileUpload(ui.FileUploadProps{...})` instead of a standard input.

### generateDetailFieldCode() (modelgen.go:2406)
Generates read-only display code for detail views:
- Relations: nil-safe display of related display field
- Bool: "Yes"/"No"
- Time: formatted date
- Pointer types: nil-safe access
- Default: `{model}DetailRow("Label", value)`

**Pattern for file fields**: Add case for `field.Input == "file"` that renders image preview (for images) or download link (for non-images).

### Upload Endpoint
- `POST /__gux_api/upload` — multipart file upload, returns `[]UploadResult`
- Auth-protected by default, CSRF-protected automatically

### File Serving
- `GET /__gux_api/files/{key}` — serves stored files
- Content-addressed: `{hash2}/{fullhash}{ext}`
- Long-term caching headers (immutable content)

## 6. CRUD Delete Flow

### handleDelete (crud.go:762)
Current flow:
1. Fetch model by ID
2. `db.Delete(item)` (GORM soft-delete if model has DeletedAt, hard-delete otherwise)
3. Audit log if enabled
4. Return 204

**CRITICAL**: No pre-delete or post-delete hooks exist. File cleanup must be injected here.

### Required Changes
1. Before `db.Delete()`: Read the record's file field values (storage keys)
2. After `db.Delete()`: Call `storage.Delete()` for each file key
3. Honor `BeforeFileDelete` hook (can prevent deletion)
4. Handle errors gracefully (don't fail record delete if file cleanup fails — log warning)

### Update Flow (handleUpdate, crud.go)
Also needs file cleanup: when a file field value changes (old file replaced), the old file should be deleted. This happens in the update handler after successful DB save.

## 8. Recommendations (Claude's Discretion)

### File Metadata Struct
```go
type FileInfo struct {
    Key         string `json:"key"`           // Storage key
    URL         string `json:"url"`           // Serving URL
    Filename    string `json:"filename"`      // Original filename
    Size        int64  `json:"size"`          // Bytes
    ContentType string `json:"content_type"`  // MIME type
}
```
Keep it simple — matches UploadResult minus Width/Height (which are image-specific). The DTO for detail views can embed this struct for file fields.

**Decision**: For simplicity in Phase 31 (single-file fields), DTOs will use `string` type for file fields (storing the storage key/path). The detail view template will generate code that calls `storage.URL(key)` to produce the serving URL. This avoids a complex metadata struct in DTOs while keeping the API simple. The UI rendering code handles image detection via file extension.

### File-Type Icon Determination
Extension-based mapping is simplest and most reliable for display:
```go
var imageExtensions = map[string]bool{".jpg": true, ".jpeg": true, ".png": true, ".gif": true, ".webp": true, ".svg": true}
func isImageFile(path string) bool { return imageExtensions[strings.ToLower(filepath.Ext(path))] }
```
Generate this as a helper function in the admin helpers file. No need for MIME detection on the display side — the storage layer already validated MIME on upload.

### Thumbnail Approach in List Views
CSS resize (not server-side) — use `object-fit: cover` on an `<img>` tag with fixed dimensions. Server-side thumbnail generation is Phase 32+ (deferred to IMG-01/IMG-02 requirements). This keeps Phase 31 simple and avoids new server infrastructure.

### Rollback on DB Save Failure
In the CRUD update/create handler, wrap the sequence:
1. Upload file (via separate upload endpoint — already done client-side before form submit)
2. Submit form data including file key
3. DB save — if fails, call `storage.Delete(newKey)` to clean up

Since uploads happen client-side before form submission (Phase 30 design), the rollback happens in the CRUD create/update handler: if `db.Create()` or `db.Save()` fails, delete the uploaded file. This requires the handler to know which fields are file fields (via `FileFields` on CRUDModel).
